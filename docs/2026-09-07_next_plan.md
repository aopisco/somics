## Priorities, in order

### 1. Land it (days, not weeks)

- **Merge #21 and #22 into `main`.** Five days of work on two stacked
  branches; every EC2 script clones the branch by name and CLAUDE.md says
  "point at main once merged". Then collapse the three EC2 ingest scripts
  (Visium, Xenium, protein) into one runner parameterised by family -- they
  are near copies and each fix had to land three times.
- **Verification report** over every spec set on the final prefix
  (`verify_atlas_ec2.sh`), read it, fix what it finds, and re-run the fold
  scripts so every registry row carries an ingest verdict. Add an `in_atlas`
  column to `datasets.csv` (section ids, atlas prefix) so the registry says
  what is queryable.
- **Publish.** Sync the final prefix to R2 (`sync_atlas_to_r2.sh` targets the
  hackathon atlas path; decide whether the 50M-row atlas replaces it or lands
  beside it), rebuild `data/corpus_index.json` and the dataset pages, and
  check both UIs against 540 sections -- the corpus builder's docstring
  assumes an atlas "small enough" to precompute; that assumption is gone.
- **Close the loop on issues**: #14 (this is the full ingestion), #16 (HuBMAP
  coverage, now real numbers), #18 (see 4), #19 (still open; the published
  colon section is still wrong upstream).
- **File the Lance compaction defect upstream** (homeobox/polycomb) with the
  repro we have: every ingest's `optimize()` can leave a fragment that fails
  filtered struct reads, and an all-null enum column cannot be compacted. The
  repair step is a workaround, not a fix.

### 2. HuBMAP imagery: the largest remaining block (1–2 weeks)

763 Histology + 356 Auto-fluorescence + 46 MIBI bone marrow = **1,165 staged
datasets, 8.5 TB, with no cells** -- pure `discrete_image`. The atlas is
obs-centric (a section is its rows, crops are pointers from rows), so an
image-only section needs a decision before an adapter:

- *Tile grid as obs*: one row per 128 px tile (`spatial_unit: other`, no
  expression), so images become queryable by tissue/donor and crop-able like
  everything else. Cheap to build on the Visium builder (a grid is a grid);
  ~1,165 sections at 10k–100k tiles each.
- *Section-only*: register the image and section without obs rows. Requires
  schema work (a section with zero obs) and the UIs would not show it.

Recommendation: tile grid, and say so in the section description. This is
also the block the DCA imaging team said they do not cover -- the doc for
Aofei proposed we implement their spec for it; the tile-grid packages are the
natural thing to also emit as DCA stores if that conversation resumes.

### 5. Quality passes worth a day each

- Disease resolution rate across the atlas (the verifier reports it per
  section); unresolved source strings become a curation list.
- Donor metadata: 10x's are all null by necessity; HuBMAP's are real. Any
  `unknown` that could be filled from a paper is a registry task.
- The `perturbation` block: every dataset so far is unperturbed; the
  literature tail will not be, and the per-dataset check must be part of its
  curation recipe.

## What not to do

- Do not ingest anything without the end-of-run repair check and without a
  follow-up pass reading `_failed.txt`; every block this week needed 2–5.
- Do not run two ingests against one atlas prefix.
- Do not re-fetch the 10x Xenium bundles the DCA team holds if that access
  ever lands; ours are staged and that duplication is already sunk.

## Addendum 2026-09-09: seed the destination prefix server-side

Every ingest run starts its destination prefix empty, so its first per-dataset
`aws s3 sync` re-uploads the whole atlas (1.1 TB, ~2 h on an m5n.4xlarge)
before the run's own delta. Measured on Xenium run 5 and the MERFISH block.
When the three EC2 scripts collapse into one, seed the destination with a
server-side copy of the base prefix first (`aws s3 cp --recursive` between
prefixes never touches the box), then the per-dataset syncs carry only deltas.
The same applies to the 2.5-3 h download of the base atlas: that one is
unavoidable while ingestion needs the atlas on local disk.
